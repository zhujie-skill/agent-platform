# ADR-006：数据库通用工具与代码内本地工具分离

- 状态：Superseded
- 日期：2026-10-02
- 被替代：[ADR-007：Agent Catalog、统一 Tool Registry 与多对多复用](./ADR-007-agent-catalog-and-tool-registry.md)

> 本文件仅保留历史决策背景；当前实现应遵循 ADR-007。

## 背景

平台未来需要接收其他团队注册的通用工具。这些团队在自己的 Git 仓库中开发并部署工具，没有本项目 Git 的访问权限。与此同时，当前项目还会包含少量只服务本项目的内部工具，不需要被其他团队发现或调用。

如果要求所有通用工具都通过本项目中的 Manifest 文件注册，外部团队将无法独立完成注册；如果把所有项目本地工具都写入中央 Registry，又会扩大公共目录、权限和版本治理的范围。

## 决策

工具分为两类：

1. 通用共享工具由 Tool Registry 数据库维护。工具通过 Control Plane 或 Registration API 注册，数据库是定义、版本、Schema、执行路由和状态的唯一权威来源。
2. 项目本地工具只存在于本地代码中，由进程内 `LocalToolRegistry` 或显式代码映射加载，不写入中央 Registry。

平台不实现本地文件与 Registry 数据库之间的同步。MCP 或 OpenAPI 工具只能在用户明确执行注册或导入时创建数据库快照，之后不会持续自动同步。

数据库只保存通用工具的调用契约和路由信息，不保存可执行源代码。执行实现可以位于平台 Built-in Executor、外部 HTTP Tool Service、外部 MCP Server 或未来的隔离 Worker。

## 结果

- 外部团队不需要访问本项目 Git 即可注册和维护通用工具；
- Gateway 在运行时只查询 Registry 数据库；
- 通用工具需要不可变版本、审计、备份和发布控制；
- 项目本地工具保持简单，不进入公共治理流程；
- 本地工具不会自动变成共享工具；需要共享时必须完成一次显式注册和发布；
- 平台不承担 Manifest 与数据库之间的漂移检测和同步复杂度。

## 备选方案

曾考虑使用 Git Manifest 作为通用工具定义来源，再同步到 Registry。该方案适合平台完全拥有的第一方工具，但不能覆盖外部团队没有本项目 Git 权限的主要场景，因此未采用。

也考虑过将所有工具都放入 Registry。该方案会让仅供本项目使用的内部函数承担不必要的版本、权限和公共目录治理成本，因此未采用。

## 重新评估条件

如果未来出现强制 GitOps、监管审批或跨环境声明式发布要求，可以为 Registry 增加显式的导入/导出能力，但不得引入隐式双向同步，也不得改变数据库作为通用工具运行时权威来源的原则，除非另立 ADR。
